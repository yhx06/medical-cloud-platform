# 多租户医疗云完整课程系统设计

## 1 目标与验收边界

本阶段把现有身份认证与租户隔离基础框架扩展为可在期末完整演示的医疗云课程系统。核心演示链是：平台创建医院，医院创建科室、医生和号源，患者预约，医生接诊并完成病历与处方，系统生成订单，患者模拟支付，医院和平台查看权限范围内的统计与审计结果。

系统通过一条 Docker Compose 命令启动 MySQL、MinIO、后端和前端。所有数据均为虚构演示数据，不接真实支付、短信、邮箱、视频问诊、AI 诊断、DICOM 或真实医疗系统。

## 2 架构与实施方式

系统继续采用 Vue 3 前端、Spring Boot 模块化单体、MySQL 和 MinIO。模块化单体保留清晰业务边界，并避免课程周期内引入服务发现、网关、分布式事务和跨服务调试成本。

后端模块如下：

- `identity`：平台管理员、医院管理员和医生账号生命周期。
- `tenant`：租户、科室和医院资料。
- `schedule`：医生排班、号源容量和诊费。
- `appointment`：患者预约、取消和容量一致性。
- `consultation`：接诊、病历、处方和更正说明。
- `order`：订单生成、取消和模拟支付。
- `file`：附件元数据、MinIO 对象和授权下载。
- `statistics`：医院指标和平台脱敏汇总。
- `audit`：关键业务事件审计。

采用纵向业务切片实施。每个切片同时交付数据库迁移、领域行为、后端 API、前端页面、权限隔离测试和用户操作反馈。实施顺序是账号与机构、排班与预约、接诊与病历、订单与支付、文件、统计与审计、容器化验收。

## 3 角色与账号管理

角色保持 `PATIENT`、`DOCTOR`、`HOSPITAL_ADMIN` 和 `PLATFORM_ADMIN`。

- 患者查询公开机构、科室、医生与号源，管理本人预约、病历、附件和订单。
- 医生查看本人号源和预约，处理本人接诊，完成病历与处方并上传附件。
- 医院管理员维护本租户资料、科室、医生账号、号源并查看本院统计。
- 平台管理员维护租户和医院管理员账号并查看脱敏汇总，不能读取病历正文、处方或附件。

本期不提供公开注册、邮箱短信验证、密码找回或自助重置。平台管理员创建医院管理员，医院管理员创建医生。新账号使用开发环境演示初始密码，数据库仅保存 BCrypt 哈希。患者使用预置演示账号。

租户或账号被停用后不删除历史数据。登录服务拒绝停用账号；受保护业务请求在关键入口重新检查账号和租户状态，避免旧 JWT 在剩余有效期内继续办理业务。

## 4 数据模型

### 4.1 机构与排班

`tenant` 保存医院名称、状态和创建时间。`department` 保存租户、名称、简介和状态，同一租户内名称唯一。医生账号关联租户和科室，并保存姓名、职称和简介等演示资料。

`schedule_slot` 保存租户、医生、科室、日期、开始时间、结束时间、容量、诊费、发布状态和乐观锁版本。号源一旦产生预约就不能物理删除，只能停用。诊费使用定点小数，不能为负数。

### 4.2 预约

`appointment` 保存患者、租户、医生、科室、号源、预约时段和诊费快照。状态为 `BOOKED`、`IN_PROGRESS`、`COMPLETED` 或 `CANCELLED`。患者同一号源最多存在一条未取消预约；取消后可以重新预约。

预约服务锁定号源记录，统计有效预约并校验容量，数据库唯一约束作为第二道保护。患者只能在接诊开始前取消。医生只能开始分配给本人且属于本租户的预约。

### 4.3 接诊与病历

`consultation` 与预约一对一，保存患者主诉、医生诊断、处理建议、草稿时间和完成时间。`prescription_item` 保存药品名称、用法、频次和用药天数。

接诊状态允许医生保存草稿和完成病历。完成后原始病历和处方不可覆盖；修改通过 `record_correction` 追加更正说明，记录原医生、时间和原因。患者只能查看自己的已完成病历。

### 4.4 订单与支付

`medical_order` 与已完成接诊一对一，金额取预约中的诊费快照，状态为 `PENDING`、`PAID` 或 `CANCELLED`。完成病历和生成订单在同一数据库事务中。

患者只能支付自己的待支付订单。模拟支付生成唯一流水号并记录支付时间，不调用第三方服务。已支付订单不退款；取消只适用于待支付订单。

### 4.5 文件与审计

`file_metadata` 保存租户、病历、上传者、原文件名、对象键、媒体类型、大小和创建时间。允许 PDF、JPG 和 PNG，单文件不超过 10 MB。

MinIO Bucket 始终私有。医生只能为本人接诊的病历上传附件，患者只能访问本人病历附件。后端授权成功后返回五分钟有效的签名下载地址。数据库写入失败时删除已上传对象；定期清理没有元数据引用的对象作为补偿。

`audit_event` 保存操作者、租户、事件类型、对象类型、对象标识、结果、请求标识和时间。登录、账号状态变化、预约状态变化、病历完成、更正、支付和文件访问需要审计。审计内容不得包含密码、令牌、主诉、诊断、处方正文或签名下载地址。

## 5 核心事务与数据流

预约流程：患者选择由服务端查询得到的号源，预约服务从号源确定租户和医生，不信任客户端提供的租户身份；服务锁定号源、检查状态、日期、容量和重复预约，再创建预约及审计事件。

接诊流程：医生从 JWT 得到身份和租户，查询本人预约并开始接诊。保存草稿不会生成订单。完成时校验病历字段，冻结原始内容，将预约置为完成，同时按诊费快照生成待支付订单和审计事件。

支付流程：患者读取本人订单，模拟支付服务以幂等方式把待支付订单置为已支付，记录流水号和时间。重复支付请求返回当前已支付结果，不重复生成流水。

文件流程：后端先校验病历归属、角色、租户、类型和大小，再将对象写入私有 Bucket 并持久化元数据。下载时重新校验访问者与病历关系，然后生成短期签名地址。

## 6 API 设计

所有接口使用 `/api` 前缀、统一响应体和分页结构。

公开认证后可查询的目录接口：

- `GET /api/catalog/tenants`
- `GET /api/catalog/tenants/{tenantId}/departments`
- `GET /api/catalog/schedule-slots`

患者接口：

- `GET|POST /api/patient/appointments`
- `GET /api/patient/appointments/{id}`
- `POST /api/patient/appointments/{id}/cancel`
- `GET /api/patient/records`
- `GET /api/patient/records/{id}`
- `GET /api/patient/orders`
- `POST /api/patient/orders/{id}/pay`

医生接口：

- `GET /api/doctor/appointments`
- `POST /api/doctor/appointments/{id}/start`
- `PUT /api/doctor/consultations/{appointmentId}/draft`
- `POST /api/doctor/consultations/{appointmentId}/complete`
- `POST /api/doctor/records/{recordId}/corrections`
- `POST /api/doctor/records/{recordId}/files`

医院管理员接口：

- `GET|POST /api/hospital/departments`
- `PUT /api/hospital/departments/{id}`
- `GET|POST /api/hospital/doctors`
- `PUT /api/hospital/doctors/{id}/status`
- `GET|POST /api/hospital/schedule-slots`
- `PUT /api/hospital/schedule-slots/{id}`
- `GET /api/hospital/statistics`

平台管理员接口：

- `GET|POST /api/platform/tenants`
- `PUT /api/platform/tenants/{id}/status`
- `POST /api/platform/tenants/{id}/administrators`
- `PUT /api/platform/administrators/{id}/status`
- `GET /api/platform/statistics`

文件下载使用 `POST /api/files/{id}/download-url`，避免把签名地址缓存为普通目录响应。

## 7 前端页面

前端使用统一应用壳，但为四类角色提供独立路由和菜单。患者端包括号源查询、预约列表、病历详情、附件和订单支付。医生端包括今日预约、待接诊、接诊编辑器、历史病历和更正。医院管理员端包括医院资料、科室、医生、号源和机构统计。平台管理员端包括租户、医院管理员和脱敏平台统计。

共享组件包括分页表格、筛选栏、状态标签、金额显示、空状态、加载状态、确认对话框和统一错误提示。路由守卫改善交互，后端授权仍是最终安全边界。未授权页面跳转到角色工作台，接口拒绝时显示稳定中文错误。

## 8 错误处理

统一错误响应继续包含 `code`、`message`、`requestId` 和可选 `fieldErrors`。新增稳定错误码覆盖账号或租户停用、号源已满、重复预约、号源不可用、非法状态转换、非本人接诊、病历已完成、订单已支付、文件类型不支持、文件过大和存储服务不可用。

未处理异常只向客户端返回通用信息，服务端记录请求标识和必要堆栈。日志不得记录医疗正文或凭据。前端根据错误码展示可操作的中文提示。

## 9 统计口径

医院统计按当前租户和日期范围计算预约总量、取消量、完成量、已支付收入和医生完成接诊数。平台统计只返回各租户的账号数、预约量、完成量、已支付收入和状态，不包含患者身份、病历内容、处方或文件信息。

课程数据量较小，统计先使用数据库聚合查询，不引入数据仓库、消息队列或缓存。统计口径以业务状态和支付时间为准，并在接口文档中固定。

## 10 测试与验收

后端遵循测试先行。领域测试覆盖状态转换、金额快照、病历冻结和支付幂等；数据测试覆盖迁移、唯一约束、租户过滤和并发容量；接口测试覆盖四角色矩阵、本人数据边界和跨租户拒绝；MinIO 适配器测试覆盖文件校验、上传、补偿删除和短期下载地址。

前端测试覆盖角色路由、查询筛选、表单校验、预约、接诊、支付和错误反馈。端到端冒烟流程覆盖平台建院、医院建科室医生与号源、患者预约、医生接诊、患者支付以及统计更新。

最终验收条件：后端测试、前端测试和生产构建无失败；一条 Docker Compose 命令启动 MySQL、MinIO、后端和前端；四类账号完成各自演示流程；跨租户访问稳定返回 403；重复预约和超额预约被拒绝；私有附件只能由授权用户获取短期地址；演示脚本可从干净数据库重复执行。

## 11 非目标

本期不实现患者公开注册、真实支付和退款、短信邮箱、视频通话、AI 诊断、DICOM、电子签名、医保结算、生产级高可用、微服务治理或真实医疗数据接入。这些能力只在报告的后续展望中说明，不进入期末系统验收。
