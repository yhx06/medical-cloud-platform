## 1. 目标、约束与完成标准

用户同意在医院启停与统计看板之后，先补持久化审计，再单独设计附件管理。目标是使期末演示中的关键操作可追踪，并展示多租户隔离、敏感信息保护和事务一致性。系统仍只使用虚构医疗、账号与模拟支付数据，不代表生产医疗合规。

继续使用课程主链：Java 8 → Tomcat 9 Servlet/JSP（SaaS）→ WildFly 10 JAX-RS/EJB（PaaS）→ JPA/JNDI → MySQL。只修改 `course/` 和直接相关说明；保留课程服务工厂与角色门面。原 `backend/`、`frontend/`、E: 工作树内原有修改、未跟踪的 `Medical Cloud API Probe.eam` 均不在本轮范围。70 台 IaaS 仍是模型，不实际启动。

完成标准是：所列关键操作产生持久化记录；成功业务与审计同事务提交；业务失败后仍能在独立事务保存安全失败记录；医院管理员只能查看本院脱敏记录；平台管理员可以查看跨院脱敏记录，但不能获取身份明细或临床内容；门户可分页、筛选，并通过真实容器/MySQL验证。

不包括附件、病历草稿/更正、结构化处方、新建医院/医院管理员、真实支付、审计导出、审计明细下钻、全站访问日志、告警产品、留存自动清理、异步消息系统、历史事件补造或密码/令牌查询。患者和医生不新增审计查询入口。注册仍保持原行为，本轮不把患者注册纳入审计覆盖。

## 2. 方案选择与组件边界

采用现有三模块中的纵向业务切片，不引入新容器或外部日志平台。

| 方案 | 取舍 |
| --- | --- |
| EJB/JPA 持久化业务审计（采用） | 能与业务事务一致提交，沿用课程组件，能实现租户授权查询 |
| 仅写服务器文本日志 | 部署简单，但不能提供结构化、按医院授权的查询，也不能保证业务与日志一致 |
| 消息队列加独立审计服务 | 有利于大规模解耦，但增加运行与补偿复杂度，超出本期课程范围 |

组件职责：

- `contract`：事件/结果枚举、脱敏行 DTO、分页响应，均使用字段白名单。
- `paas/audit`：审计实体、事务内成功写入、独立失败写入、请求上下文、筛选校验与授权查询。持久化逻辑和 DTO 脱敏分开。
- 现有业务 EJB：在权限和状态校验之后，根据服务端查询的真实对象确定归属，在本事务内记录结果。不改变原锁顺序和状态机。
- JAX-RS 边界：为受审计操作建立服务端请求标识，接入认证/业务失败记录，保留原错误语义。查询和普通目录读取不产生审计记录。
- `portal`：增加独立 `AuditWorkspace` 与 JSP 审计区，通过 `PaasClient` 访问 PaaS，不直连数据库；不将逻辑继续堆入 `PortalServlet`。
- `deploy`：新增只加表的受保护迁移与专项验收说明。保留 `hibernate.hbm2ddl.auto=validate`。

不把 JPA 实体直接作为 API 返回值，不让 JSP 根据业务列表推测操作历史。

## 3. 事件覆盖与业务语义

路径均相对现有 `/paas/api`。除登录外，以下覆盖现有 12 个业务写入口；资源撤回/启停包含在原 update 操作内，不新增业务接口。

| 事件类型 | 入口 | 成功目标与归属 |
| --- | --- | --- |
| `LOGIN` | `POST /auth/login` | 认证通过的账号；医生/医院管理员为本人医院，患者/平台为全局 |
| `TENANT_STATUS_CHANGE` | `PUT /platform/tenants/{id}/status` | 实际目标医院 |
| `DEPARTMENT_CREATE` | `POST /hospital/departments` | 新科室、本人医院 |
| `DEPARTMENT_UPDATE` | `PUT /hospital/departments/{id}` | 授权科室、本人医院 |
| `DOCTOR_CREATE` | `POST /hospital/doctors` | 新医生账号、本人医院 |
| `DOCTOR_UPDATE` | `PUT /hospital/doctors/{id}` | 授权医生账号、本人医院 |
| `SLOT_CREATE` | `POST /hospital/slots` | 新号源、本人医院 |
| `SLOT_UPDATE` | `PUT /hospital/slots/{id}` | 授权号源、本人医院 |
| `APPOINTMENT_BOOK` | `POST /patient/appointments` | 新预约、服务端号源归属医院 |
| `APPOINTMENT_CANCEL` | `POST /patient/appointments/{id}/cancel` | 本人预约、预约归属医院 |
| `CONSULTATION_START` | `POST /doctor/appointments/{id}/start` | 本人本院预约 |
| `CONSULTATION_COMPLETE` | `POST /doctor/appointments/{id}/complete` | 新病历、预约归属医院 |
| `PAYMENT_PAY` | `POST /patient/orders/{id}/pay` | 本人账单、账单归属医院 |

一次受审计请求原则上只有一条结果记录。完成接诊产生病历与订单，记一条完成接诊事件，不另外增加订单事件；不能据此把同一请求计成两次操作。令牌校验不是登录，不为每个 API 重复生成 `LOGIN`。

结果使用 `SUCCESS`、`NO_CHANGE`、`FAILED`。`NO_CHANGE` 表示合法请求未改变业务状态，例如已付订单重复支付、医院已经处于目标状态。此类请求仍可记一条独立访问结果，但不能伪造第二次状态变化或修改首次支付时间。其他接口仍按原状态机执行，不为记录审计改变重复提交的成功/冲突语义。

数据库回滚的操作不能留下 `SUCCESS`/`NO_CHANGE`。既有历史业务不补造审计，页面说明“仅记录审计功能启用后的操作”。

## 4. 数据结构与隐私

新增 `audit_event`，使用 InnoDB。字段设计如下：

| 字段 | 类型与约束 | 含义 |
| --- | --- | --- |
| `id` | `VARCHAR(36)` 主键 | 服务端 UUID |
| `request_id` | `VARCHAR(36)` 非空 | 单次 PaaS 请求的服务端 UUID |
| `actor_id` | `VARCHAR(36)` 可空 | 已验证操作者的内部账号 ID；未认证时为空 |
| `actor_role` | `VARCHAR(32)` 可空 | 当时认证角色快照；未认证时为空 |
| `tenant_id` | `VARCHAR(36)` 可空 | 已验证的医院范围；全局/未知时为空 |
| `event_type` | `VARCHAR(64)` 非空 | 服务端事件枚举 |
| `object_type` | `VARCHAR(32)` 非空 | 服务端对象类型枚举 |
| `object_id` | `VARCHAR(36)` 可空 | 已验证目标 ID；失败事件统一为空 |
| `result` | `VARCHAR(16)` 非空 | 三种结果之一 |
| `reason_code` | `VARCHAR(32)` 非空 | 白名单结果码，不是异常正文 |
| `recorded_at` | `DATETIME(6)` 非空 | 服务端记录时间，按课程上海时区持久化 |

成功结果码为 `OK`，无变化为 `UNCHANGED`；失败只使用 `UNAUTHORIZED`、`FORBIDDEN`、`BAD_REQUEST`、`CONFLICT`、`INTERNAL_ERROR`。应用显式校验枚举和长度，不依赖 MySQL 5.6 对 CHECK 的支持。不使用 JSON 列或新版本专属 SQL。结构以 MySQL 5.6 为兼容目标，未在 5.6 实测前不得声称已验证。

对象类型依事件依次使用 `ACCOUNT`、`TENANT`、`DEPARTMENT`、`DOCTOR_ACCOUNT`、`SLOT`、`APPOINTMENT`、`CLINICAL_RECORD`、`PAYMENT_ORDER`；创建和更新同类对象使用相同类型，开始接诊使用 `APPOINTMENT`，完成使用 `CLINICAL_RECORD`。登录成功的 object_id 为认证账号 ID；失败只保留事件对应的对象类型，不保留对象 ID。

索引为全局 `(recorded_at, id)`、医院 `(tenant_id, recorded_at, id)` 和 `(event_type, result, recorded_at, id)`；唯一约束为 `(request_id, event_type)`，防止同一次请求双写。客户端重发会生成新请求 ID，不把此约束当业务幂等键，也不根据浏览器传来的标识吞掉新请求。

不设置指向业务表的外键或实体关系：审计只存标量快照，不能因业务删除级联丢失，独立失败事务也不能因外键检查等待业务锁。账号与医院归属的可信性由业务服务在读取、授权时保证。

应用仅追加审计，不提供更新或删除功能；不承诺数据库管理员不能改表，也不宣称具备防篡改存证。课程演示保留新增记录，增长与留存策略仅在后续展望说明，不自动清理运行数据。

禁止保存用户名、患者姓名、联系方式、密码或哈希、初始密码、令牌、Authorization、Cookie、主诉、诊断、建议、备注、处方、金额明细、请求/响应正文、原始 URL、查询参数、异常堆栈或签名下载地址。不设置任意自由文本/metadata 字段。日志故障提示只记录安全请求 ID 与白名单故障类型，不输出异常链或实体。

内部数据库 ID 只用于受控技术对账，不向任一审计查询 DTO 返回 `actor_id` 或 `object_id`。界面操作者仅展示角色名称，例如“患者（已脱敏）”“医生（已脱敏）”，目标仅展示对象类型。平台与医院响应均不联表读取账号姓名、病历或患者资料。允许返回审计自身 ID、请求 ID、授权医院 ID/名称、事件、结果、原因、时间和角色标签；它们不提供私有业务对象的定位入口。

## 5. 请求关联、事务与失败处理

### 5.1 请求关联

PaaS 为每次受审计操作及新增审计查询请求生成 UUID，放入受控请求上下文；不信任或回存客户端提供的 `X-Request-ID`。同一请求的审计、错误体 `requestId` 和响应 `X-Request-ID` 必须一致。新响应头是加法兼容，现有成功体不改；其他旧接口不为本轮关联功能进行全面改造。

审计上下文仅含标量信息、服务端事件枚举及已验证归属；请求结束释放，不使用 EJB 实例字段缓存当前用户或全局可变上下文。JAX-RS 到 EJB 显式传递本次上下文，避免容器线程复用串号。现有内部便利调用可以自行创建服务端上下文，但不得绕过生产审计写入。未包含请求上下文的普通错误仍由原 mapper 生成安全 UUID。

### 5.2 成功写入

成功记录由业务 EJB 在原 JTA 事务内调用 `MANDATORY` 审计写入器，与业务数据使用同一 JNDI 数据源。不采用独立成功事务、异步提交或 HTTP 响应后补写。登录成功也在认证服务事务内写入，审计失败时不能发放可用成功响应。

若成功审计插入失败，抛出明确要求回滚的基础设施异常，将业务与审计全部回滚，API 返回安全 500。必须验证 WildFly 真实 EJB 异常包装/事务规则，不能仅依赖直接 new 对象的单元测试。不得将审计不可用作为普通 `IllegalStateException` 错报为 409。

保留已有“医院 → 科室 → 医生 → 号源 → 预约 → 订单”的锁顺序。审计插入位于业务校验与更新之后，不反向取得业务行锁；不在保有业务锁时调用独立失败事务。

### 5.3 失败写入

受审计资源在认证或业务 EJB 调用失败返回后，调用独立 `REQUIRES_NEW` EJB 保存 `FAILED`。真实容器调用必须已结束原业务事务并释放锁；不能在 EJB 自调用或仍持锁的 catch 中假装开启新事务。只保存标量上下文，不传递 JPA 实体，也不再查询失败对象。

登录失败统一记匿名 `LOGIN/FAILED`，不回存用户输入的用户名，也不因错误密码去披露该用户名是否存在。缺失/过期/非法令牌的业务尝试同样没有操作者与医院归属。

认证通过的医生/医院管理员失败可归入已验证的本人医院。平台管理员失败、患者尚未完成对象归属验证的失败为全局记录。患者已在业务服务内验证本人对象与医院归属后，才可把该安全医院范围带出用于失败记录；跨院/非本人/不存在目标不能据请求 ID 查询目标医院。所有失败记录的 `object_id` 都为空，不保存攻击者提供的路径对象标识。

失败事务不可用时维持原 HTTP 错误码，不用审计故障掩盖原 401/403/400/409；记录一次无敏感内容的运行告警。数据库整体不可用时无法保证持久化失败记录，这一限制要在报告中写明，不宣称绝对不丢失。不重试业务，不无限重试审计，也不为同一次失败重复插入。

失败审计只覆盖已进入上述资源操作边界的认证、请求校验和业务调用错误；JSON 解码前失败、404、415、任意 GET、网络中断不属于本轮操作审计。业务 EJB 已提交成功后的 DTO 装配/响应传输故障不能再记成业务 `FAILED`；此时保留真实成功审计，仅记安全运行故障。对接时必须区分业务调用阶段和提交后的展示阶段。

## 6. 授权查询、筛选与 API

新增 `GET /hospital/audit-events` 和 `GET /platform/audit-events`，成功响应沿用 `{code,message,data}`；`data` 包含安全 `items`、`total`、`page`、`size`、规范化 `from/to`、时区。无修改、删除、详情或按业务 ID 搜索接口。

共有筛选参数为 `from`、`to`、`eventType`、`result`、`page`、`size`。医院接口显式拒绝 `tenantId`；平台接口可用已存在的合法 UUID `tenantId` 筛选医院，未提供则包含所有医院及全局事件。有效 UUID 但医院不存在返回 400，不退回全平台；不增加仅查询全局事件的专用选项。

先认证，再检查角色/数据库中当前启用账号，再解析筛选与分页。医院范围来自数据库账号归属，合法账号在医院 `ACTIVE` 或 `DISABLED` 时都可历史只读；账号停用/归属失效仍拒绝。平台不能借此调用患者/医生临床明细接口。患者、医生和错误管理角色为 403，无效认证为 401。

日期沿用统计规则：真实有效的 `yyyy-MM-dd`，两端均未提供为上海今天及前 29 天，只给一端为 400；首尾包含，范围 1–366 个自然日，数据库条件是上海日期的半开区间。限定可存入 MySQL 的年份及可构造的次日上界，不把非法输入当默认值。`recorded_at` 是操作记录时间，不是承诺的事务提交顺序；JVM/JDBC 与课程数据库上海时区一致，API 显式格式化带 `+08:00` 的时间，不依赖默认 JSON 时间戳行为。

`eventType`、`result` 空白视为缺省，非空只能是对应枚举。page 默认 1，size 默认 20、范围 1–100；使用原始字符串参数，认证后解析，long 计算组合 offset 并限制为 `Integer.MAX_VALUE` 内。新接口拒绝不支持和重复的筛选参数，不能允许第二个 tenantId 偷换范围。非法值为 400，角色不符优先 403，未认证优先 401；真实 RESTEasy 路由测试覆盖该顺序。

WHERE 条件同时用于 COUNT 与分页列表，参数化查询；按 `recorded_at DESC, id DESC` 稳定排序。单次响应在经核对的 REPEATABLE_READ 只读 JTA 快照下执行，不锁业务表；跨刷新可以出现新记录，不承诺页面间固定快照。查询只投影 DTO 白名单和必要医院标签，不加载 Account/ClinicalRecord，不受原业务 100/200 行截断影响。

## 7. 门户交互与降级

平台和医院首页增加“操作审计”导航及独立卡片，沿用现有外部 CSS/JS 和输出转义。普通 GET 表单即可筛选、重置和翻页，无需 JavaScript。平台可选医院，医院不展示医院范围输入。参数使用 `auditFrom/auditTo/auditEventType/auditResult/auditPage/auditSize/auditTenantId`，与统计、医院列表、订单筛选隔离。

表格显示记录时间、授权医院标签、操作者角色、操作类型、目标类型、结果、原因和请求标识。不提供“查看病历/患者”链接。全局事件医院列显示“全局/归属未验证”，不猜测归属。日期筛选是记录时间，提示包含 `NO_CHANGE` 的访问结果不能当作新业务数量。

空结果明确显示“该范围内暂无审计记录”；接口故障显示“审计服务暂时不可用”，不能伪装为零。非法筛选保留转义输入与错误提示，不自动扩大范围。翻页保持有效的本审计筛选，不覆盖其他分区的筛选。

审计区域 500/超时不清空已有订单或统计；401 则立即执行现有私有数据清理和重新登录路径，将新审计行、筛选与错误属性加入清理名单。服务端再验证角色，不能只靠不显示菜单防越权。仅查询不新增 CSRF 写表单；现有业务写表单 CSRF 规则保持。

小屏由表格自身横向滚动，带可聚焦滚动区、标题、表头和键盘焦点样式；桌面/390px 和无脚本表单访问分别验证。不引入远程资源依赖。

## 8. 迁移与部署安全

新库 `schema.sql` 增加同一审计表定义；已有 P0 完成版库使用独立 `002_audit_events.sql` 和保护性升级脚本，不能重跑初始化/seed。迁移只增加新表、索引及 JPA 实体声明，不更新旧业务行，不伪造历史。

按用户2026-10-04最新要求，今后不再新增或修改 PowerDesigner 图。现有 PDM、EAM、ER 导出图和相关绘图工具保留不动；新增 audit_event 结构以版本化SQL、JPA映射、结构测试和文字说明交付，不宣称旧8表模型代表新增后的数据库。审计表仍不添加业务外键，原8表与14条关系不改。

6. 未认证、无效账号、登录失败为匿名，不存用户名；跨院/非本人/不存在对象的失败 object_id 为空，tenant 不取自路径或请求。
7. 两医院隔离、平台全局/按院范围、DISABLED 医院历史读取、停用账号与过期令牌拒绝；查询投影不读取临床数据。
8. 日期、闰日、上海午夜、默认30天、366/367天、单端日期、枚举、重复/未知参数、分页边界及 long offset；匿名坏参数401、错误角色403、管理员坏参数400。
9. 同一请求只有一条结果；审计/错误体/响应头请求 ID 一致，伪造客户端请求 ID 无效；并发不同用户/线程不串归属。
10. 提交成功后模拟响应装配故障不新增 FAILED，不把网络重发误算一次请求；数据库故障不泄露异常内容、不覆盖原失败码。
11. 新旧库迁移、完整目标核对、备份失败不执行DDL、残缺表拒绝、已升级重复执行无写入；业务表行数与既有数据不变。
