# 医疗云课程版 P0 功能补全设计

## 1. 目标、依据与边界

本设计承接需求分析说明书的 P0 条目和已运行的课程版，不重新搭建另一套系统。目标是让四类角色在教师要求的 JDK 8、Tomcat 9、WildFly 10、JNDI/JPA、MySQL 链路上，完成“医院维护资源 → 患者查号预约或取消 → 医生接诊写病历 → 生成订单并模拟缴费 → 各角色查询”的完整演示。成功标准是页面和接口均可走通、跨租户数据不泄露、最后号源不超卖、既有演示数据可保留升级，并能给期末报告提供测试和运行证据。

本次只补课程版 `course/` 的 P0 缺口，保持 `backend/` 和 `frontend/` 原 Java 21/Vue 版不变；不接真实患者、真实支付网关或真实诊疗流程。P1 的对象存储、统计、审计及 P2 的 AI、评价继续延期。两家现有演示医院可继续使用；不在本轮增加自助开设医院或平台级租户审批。

本设计覆盖以下需求编号：`FR-AUTH-03`，`FR-TEN-02/03/04`，`FR-APT-01/03/04`，`FR-CON-01/02/04`，`FR-ORD-02/03`。已实现的登录、角色授权、预约、医生预约查询、接诊完成、患者单条病历/订单查询和模拟支付必须回归，不因补全而退化。

## 2. 选用方案与系统边界

选择在现有三模块 `contract`、`paas`、`portal` 上纵向补齐，不引入新框架或服务。Tomcat 的 Servlet/JSP 只做表单、会话、CSRF 与展示；WildFly 的 JAX-RS 入口校验请求，EJB/JPA 承担权限、事务和业务规则；MySQL 存储状态。`CloudServiceFactory` 和现有角色门面保留。所有机构归属均从登录令牌重新读取的账号与数据库关系判定，不能信任浏览器传入的 `tenantId`。

没有采用“只改页面、继续由种子 SQL 维护资源”的方案，因为无法满足医院管理员维护 P0；也没有迁回 Spring Boot/Vue，因为不能验证教师的双容器链路。功能按资源管理、预约、诊疗/订单三个业务单元组织；一个单元的页面、契约、服务和数据变更一起交付。现有接口保持兼容，仅为新字段增加可选或新接口，不能让原演示脚本失效。

## 3. 角色与业务规则

### 3.1 患者注册

公开注册只可创建 `PATIENT` 账号；门户收集用户名、密码和确认密码，传给 PaaS 的只有用户名、密码，不接受角色、机构、状态字段。用户名为 3–64 位 ASCII 字母、数字或下划线，且全局唯一；密码为 8–72 个 UTF-8 字节，按现有 BCrypt 方案存储，禁止明文日志与响应回显。门户与 PaaS 一致校验，最终以 PaaS 为准。重复用户名返回明确的冲突，不覆盖旧账号。注册成功进入登录页，由用户登录；不自动授予管理身份。注册和登录均在 PaaS 验证账号为 `ACTIVE`。

### 3.2 医院资源管理

医院管理员只能读写其账号所属且启用的机构。可以新增、改名、停用本机构科室；创建医生账号与档案、修改显示名或所属科室、停用医生；创建并发布排班号源、修改尚无有效预约的号源、撤回未来尚无有效预约的号源。医生的机构由管理员会话确定，所属科室必须在同一机构且启用；医院管理员不能创建平台管理员或跨机构医生。新医生账号使用一次性展示的初始密码，数据库只保存 BCrypt 哈希；课堂演示不实现邮件发送或强制改密工作流。

已被号源或历史业务引用的科室和医生采用逻辑停用，不删除行。已有有效预约的号源不允许更换医生、科室、日期、时段、费用或减少容量，也不允许撤回；避免预约快照和临床归属变化。无预约号源修改后仍须满足同医生同日同开始时间的唯一约束，容量须为正，结束时间须晚于开始时间。停用医生后不再提供新预约，但已有预约仍保留历史；管理员需在停用前看到未完成预约提示，且存在 `BOOKED` 或 `IN_PROGRESS` 预约时必须拒绝停用。科室同理，在存在有效未来号源或未完成预约时必须拒绝停用。

### 3.3 号源查询、预约、取消和历史

患者可按机构、科室、医生、日期筛选公开号源，只展示启用机构、科室、医生、已发布、未过期且有余量的数据。筛选参数只能缩小公开范围，不能绕过服务端的状态校验。目录显示容量与实时剩余数；此数字仅供查看，预约时仍以事务内当前数据为准。

预约沿用“先锁号源，再检查有效预约并创建”的事务顺序。有效占位状态为 `BOOKED`、`IN_PROGRESS`、`COMPLETED`；`CANCELED` 不占容量。同一患者同一号源同时最多有一条非取消预约。允许患者取消自己的 `BOOKED` 预约，且必须在号源开始时间之前；`IN_PROGRESS`、`COMPLETED`、已开始或已过期号源不可取消。取消保留原预约行及其 `CANCELED` 状态，释放一个名额；患者可在尚有余量时重新预约同一号源，产生新预约 ID，旧记录继续显示在历史中。取消不触发退款：订单只在接诊完成后生成，而可取消状态尚未接诊。

患者历史列表包含各状态预约及必要的机构、科室、医生、时间展示字段，仅列本人，按预约时间倒序；医生列表只列本人的预约，包含取消标记但不可开始已取消预约。重复取消返回 `409 CONFLICT`，不再次释放容量；客户端可刷新列表获取最终状态。

### 3.4 接诊、病历和订单

所属医生对 `BOOKED` 预约开始接诊时记录服务端时间 `started_at`，状态变为 `IN_PROGRESS`；重复开始或取消后开始返回冲突。接诊完成时要求填写主诉、诊断和诊疗意见，备注可空；现有 `diagnosis`、`advice` 字段继续使用，新字段仅补充。完成、创建唯一病历、创建唯一订单在同一事务中完成；重复完成不能生成第二份记录或订单。病历应记录提交时间，医生可查询本人机构内自己接诊形成的病历；患者原有按预约查看本人病历入口保留。没有完成接诊的预约无病历和订单。

订单继续为模拟支付。第一次从 `UNPAID` 转为 `PAID` 时记录 `paid_at`；重复支付返回同一 `PAID` 订单和首次支付时间。医院管理员只可按其所属机构查询订单，可按状态和日期筛选并看到订单状态、金额、关联预约和支付时间，不可触发患者支付。患者原有按预约查看本人订单与本人支付入口保留。

## 4. 接口与页面契约

所有新增 API 延续 `{code, message, data}` 成功体和带 `requestId` 的错误体。除注册与公开目录外均需 Bearer 令牌。请求参数采用明确字段与服务端校验；列表默认有上限和稳定排序，避免一次读取全部历史数据。新接口的具体 Java DTO 名称由实施计划决定，以下路径和权限作为外部契约。

| 方法与路径 | 功能 | 授权 |
| --- | --- | --- |
| `POST /auth/register` | 创建患者账号；仅接收用户名、密码 | 公开 |
| `GET /catalog/slots?tenantId=&departmentId=&doctorId=&date=` | 筛选可预约号源，返回剩余数 | 公开 |
| `GET /hospital/departments`、`POST /hospital/departments`、`PUT /hospital/departments/{id}` | 本院科室列表、新增、改名或停用 | 本院医院管理员 |
| `GET /hospital/doctors`、`POST /hospital/doctors`、`PUT /hospital/doctors/{id}` | 本院医生列表、创建、修改或停用 | 本院医院管理员 |
| `GET /hospital/slots`、`POST /hospital/slots`、`PUT /hospital/slots/{id}` | 本院号源列表、发布、修改或撤回 | 本院医院管理员 |
| `GET /patient/appointments`、`POST /patient/appointments/{id}/cancel` | 本人预约历史、取消未接诊预约 | 患者本人 |
| `GET /doctor/records` | 本人病历列表，可按日期筛选 | 该机构所属医生 |
| `GET /hospital/orders` | 本院订单列表，可按状态和日期筛选 | 本院医院管理员 |

现有 `POST /doctor/appointments/{id}/complete` 请求体扩展 `complaint`、`notes`，保留 `diagnosis`、`advice`。新门户表单要求主诉，PaaS 为兼容现有调用允许旧请求不带 `complaint` 并存为空值；备注始终可空。这样现有演示脚本仍能工作，新流程又可展示完整病历。现有患者病历和订单详情接口不改路径。所有 ID 在 PaaS 查询资源后重新校验所属机构和主体；不存在或不属于调用者的私有对象统一返回不泄露资源是否存在的拒绝结果。

Tomcat 增加注册页和入口、患者筛选/历史/取消表单、医院科室/医生/排班/订单页、医生接诊表单与本人病历页。所有修改型表单继续执行会话角色检查、CSRF 校验、UTF-8 解码、输出转义和提交后重定向；错误显示公共中文提示，不回显密码或其他机构私有数据。页面不直连数据库，不把医生/机构 ID 作为授权依据。

## 5. 状态、并发与数据迁移

`appointment.status` 增加 `CANCELED`，合法转换为 `BOOKED → CANCELED`、`BOOKED → IN_PROGRESS → COMPLETED`。取消与预约针对同一个号源都先获取号源行写锁，再获取所需预约行锁并做当前读；接诊开始与取消竞争时，必须使用一致的锁顺序，确保只有一个状态转换提交。有效预约数按非 `CANCELED` 行计算，容量检查和同患者重复检查必须在号源锁保护下用当前读完成。数据库现有 `(patient_id, slot_id)` 唯一约束需改为普通索引；否则取消后无法保留历史并重约。由于 MySQL 5.6 没有合适的部分唯一索引，应用事务以号源行锁保证“最多一条有效预约”，并用并发测试覆盖。`clinical_record.appointment_id` 与 `payment_order.appointment_id` 的唯一约束保留。

采用保留数据的版本化增量 SQL 迁移，不把 `CREATE TABLE IF NOT EXISTS` 当作旧表升级。迁移增加预约开始接诊时间、病历主诉/备注/完成时间、订单支付时间等可空列，先兼容旧行；旧 `PAID` 订单的 `paid_at` 保持空值并在界面标为“历史时间未知”，不得伪造支付时间。更新 `schema.sql` 使新库直接得到最终结构；增量脚本针对已有隔离课程库，先校验约束和列状态、备份、再执行明确的 DDL，重复运行应能识别已迁移状态或明确安全停止。PowerDesigner `.pdm`、导出关系图和课程架构说明同步更新。迁移不得清空或重写现有预约、病历、订单和历史演示数据；旧版并发验收遗留的隔离库测试行亦不自动删除。

`schedule_slot` 仍以容量原值加有效预约计数计算余量；不额外保存可变剩余量，以免取消和并发写出双真相。应用明确采用 `Asia/Shanghai` 课程时区判断日期和截止时间，不依赖操作系统默认时区；数据库时间字段与接口展示依此统一。密码和令牌不进入报告截图；所有测试使用虚构数据。

## 6. 错误与安全约定

缺字段、非法格式、负容量和不合法日期为 `400 BAD_REQUEST`；未认证或停用账号为 `401 UNAUTHORIZED`；角色不符、跨机构或非本人资源为 `403 FORBIDDEN`；重名、无余量、重复有效预约、状态不可转换和受引用资源不可停用为 `409 CONFLICT`。未知故障为 `500 INTERNAL_ERROR`，只在服务端日志保留详情。门户显示可理解的公共错误，不把数据库异常、SQL 或堆栈返回浏览器。PaaS 每次受保护请求重新读取账号状态；新管理接口也做同等检查。

由于是课程演示，登录仍使用现有一小时 HMAC 令牌与 BCrypt，不引入短信、邮箱验证、找回密码、真实支付和医疗合规声明。注册接口须避免任意角色注入；医院管理员即使猜出其他机构的资源 ID 也不能读取或修改。展示用病历和订单只用虚构数据，报告示例需脱敏。

## 7. 测试与验收

单元与持久化测试覆盖注册唯一性、角色注入、机构边界、医生/科室/号源关联、资源停用条件、目录筛选、取消截止、重复取消、取消后重约、患者和医生历史、病历字段与时间、医院订单过滤、`paid_at` 幂等。并发测试用最后一个号源同时预约以及同一号源取消/重约竞争，核对有效预约数不超过容量、同患者最多一条有效预约。既有 27 项测试和原演示脚本继续运行。

真实验收在隔离 JDK 8/Tomcat 9/WildFly 10/MySQL 环境进行：用新患者注册，医院管理员发布未来号源，患者筛选并预约，取消后验证余量恢复、再次预约，医生开始并完成接诊，患者查看病历并模拟支付，医院管理员查看本院订单；再用另一医院账号尝试访问这些资源，应拒绝且不泄露内容。执行增量迁移前后核对旧表行数、代表性预约/病历/订单及旧支付状态；演示结束保存构建测试结果、双容器日志、接口响应和页面截图作为报告证据。

交付物为课程版源代码与测试、数据库新建及增量脚本、更新的 PowerDesigner 源模型与图、接口目录、部署/验收说明和演示脚本。实施计划按上述三个业务单元分步安排，每步可独立测试；全部 P0 完成后再讨论 P1/P2。
