# 医疗云课程版：医院开通与医院管理员维护设计

日期：2026-10-18。状态：用户已确认书面设计，并已批准配套实施计划，开始实现。批准对象为设计提交309b675，本次状态更新不改变其业务规则。

## 1. 目标、确认事项与边界

本批补齐课程演示链的起点：平台管理员从平台页面一次创建医院及首位医院管理员，由新管理员继续使用已有科室、医生和号源管理功能。不要求修改数据库或使用预置医院才能演示开通。系统继续用于虚构课程数据，不接入真实医疗机构。

用户已确认：

- 医院与首位管理员一次开通；失败整体回滚，不留下没有管理员的新医院。
- 平台管理员设置初始密码；服务器仅保存 BCrypt 哈希，成功响应与页面不回显密码。现有医生随机初始密码流程不变。
- 只有平台管理员可以增补、启用和停用医院管理员；医院冻结时仍可恢复管理员账号。
- 禁止停用该院最后一位启用管理员。暂停全院业务使用已有医院冻结功能。
- 沿用课程架构，在平台页提供开通、管理员列表与启停；重复提交返回同一开通结果。

不纳入本批：密码找回或重置、首次登录改密、邮箱短信交付、医院自助注册、平台管理员账号维护、角色切换、账号迁院、资料编辑、患者/医生身份规则重设计。既有医院冻结、临床、订单、附件和统计业务语义不变；仅补充与管理员停用直接相关的写入时身份复核。

本次批准仅允许细化设计。书面设计经用户确认后才编写实施计划；计划确认后才实施。既有诊疗/附件验收结果独立保留，本文件不批准另一个验收流程调整，也不表示全系统完成。

## 2. 架构选择与现状依据

采用现有 Java 8、Tomcat 9 Servlet/JSP 门户、WildFly 10 JAX-RS/EJB/JPA、MySQL 的纵向切片，不引入新的服务或容器。

不选“先建医院，再另建首管理员”：会产生中间不可用状态与补偿流程。不选独立身份微服务：本批无需增加跨服务事务与部署成本。两者都不进入实施范围。

已检查当前课程源码：PlatformTenantService/Resource 只有医院列表与状态变更；Account 已能表达 HOSPITAL_ADMIN、所属医院和 ACTIVE/DISABLED，Tenant 已有名称与状态；PlatformWorkspace/platform.jsp 已提供医院分页与冻结操作。因此复用现有实体和平台页面，仅增加开通业务及专门的安全 DTO，不把 Account 实体直接返回给浏览器。

组件职责：

- contract：新增开通/增补/管理员列表 DTO、请求校验契约、事件及错误码。
- PaaS：专门的 PlatformAdministrationService 负责开通、幂等、管理员查询与状态变更；复用身份、审计和事务边界。现有 PlatformTenantService 保留列表/冻结职责。
- 门户：新增独立 PlatformAdministrationServlet/Workspace 及表单视图，平台首页提供入口，复用登录会话、CSRF、中文提示、转义和样式。
- 数据层：复用 tenant/user_account；新增一张仅保存非密码操作信息的幂等记录表。

## 3. 业务规则

### 3.1 开通与增补

新医院与首管理员均为 ACTIVE；管理员角色固定 HOSPITAL_ADMIN，tenant_id 只能来自本次新建医院。客户端不能指定角色、状态、账号编号或任意 tenant_id。

对已有医院增补管理员时，医院只由 URL 中的目标编号确定，账号也默认 ACTIVE。平台的管理员维护属于控制面操作，ACTIVE 或 DISABLED 医院均允许增补、启用及合规停用；冻结医院不会因此自动解冻，也不会恢复科室、医生或号源状态。

医院名称原文先拒绝控制字符与非法代理字符，再去除两端普通空格；结果为 1–100 个 Java UTF-16 单元，不做大小写或 Unicode 归一化。医院名称不是唯一标识，可以同名，列表同时显示编号以区分。用户名采用已有规则 [A-Za-z0-9_]{3,64}，不自动去空格；全系统不区分 ASCII 大小写唯一，复用 uk_course_username，不能与患者、医生或其他管理员重名。

密码沿用已有课程注册的 8–72 UTF-8 字节范围，拒绝控制字符和非法代理字符；不裁剪、不归一化、不记录请求对象的全文。门户增加一次确认输入，确认值仅在该次请求内比较，不传入 PaaS。PaaS 独立校验实际密码，不能依赖页面校验。

### 3.2 管理员状态与冻结

账号状态仅 ACTIVE/DISABLED，变更请求带 status 与 expectedStatus。目标已处于期望结果时返回当前结果并记 NO_CHANGE；实际需要改变而 expectedStatus 过期时返回 409。

ACTIVE→DISABLED 前必须确认同院还存在另一位 ACTIVE 的 HOSPITAL_ADMIN；医生、平台账号、其他医院账号及 DISABLED 管理员均不计入。此保护在医院冻结时也适用。历史上已有零启用管理员的医院不通过迁移自动创建账号，可由平台增补或启用管理员修复；已停用目标的重复停用不受“最后一位”规则阻挡，因为它没有进一步减少启用人数。

停用账号不删除历史数据、不迁移业务归属、不改密码。旧 JWT 不再允许新受保护请求；处于竞争中的医院资源写入按第 6 节确定先后顺序。

## 4. 重复提交与密码保护

医院开通与管理员增补均需要 operationKey：服务端门户生成的非全零规范小写 UUID，API 调用者也必须提供同样格式。它用于识别一次业务意图，不代替 CSRF、身份认证或授权，也不允许据此修改已有账号。

新增 hospital_admin_operation 表记录已提交操作。唯一键为 (actor_id, operation_key)，两类创建操作共用命名空间。只有创建事务全部成功才保存该记录。

相同已认证平台账号、相同 key、相同操作类型与规范化输入的重试返回原医院/管理员编号及创建时名称、用户名，不再次建院或增补账号、不重新设置密码；新的审计请求记 NO_CHANGE。相同 key 改操作类型、医院、名称、用户名或密码，返回 OPERATION_KEY_CONFLICT（409）。不同 key 不把“用户名已存在”误当成功。

密码不进入操作表，也不生成快速摘要。重试时在锁保护内用原账号的 BCrypt 哈希校验本次提交密码；用户名比较使用 ASCII 大小写等价，名称比较使用修剪后的精确值。本批不支持密码重置；若后续功能改变了账号密码，旧创建请求可能返回冲突，不得借此重设密码或新建账号。重试不受医院后来冻结、目标账号后来停用的影响，且不自动改变这些状态。

重试还必须核实原账号仍为 HOSPITAL_ADMIN、所属医院与操作记录一致；关联异常通用拒绝，不用其他医院账号的哈希验证请求。

创建响应仅包含不可变的创建结果：tenantId、hospitalName、administratorId、username，不含密码、哈希或易误导的原始 ACTIVE 状态；实时状态从列表读取。增补响应采用相同安全结果结构。两次成功返回相同业务结果，requestId 则是各次请求新生成的标识。

门户失败页面可以保留名称、用户名和 operationKey，但密码及确认密码必须为空。遇到超时、响应丢失或未知结果，提示用相同 key 和原密码重试，不能自动生成新 key 或自动重发业务 POST。成功后采用 POST→Redirect→GET；刷新成功页不重复创建。

## 5. 数据结构与保护性升级

新增 hospital_admin_operation，字段全部 NOT NULL：

| 字段 | 类型与含义 |
| --- | --- |
| id | VARCHAR(36)，主键，服务端 UUID |
| actor_id | VARCHAR(36)，外键到 user_account；保留现有编号字符集/排序规则 |
| operation_key | VARCHAR(36) ASCII/ascii_bin，规范 UUID |
| operation_type | VARCHAR(32) ASCII/ascii_bin，HOSPITAL_OPEN 或 ADMIN_ADD |
| tenant_id | VARCHAR(36)，外键到 tenant |
| admin_id | VARCHAR(36)，外键到 user_account，本次创建的管理员 |
| hospital_name | VARCHAR(100)，创建结果名称快照 |
| admin_username | VARCHAR(64)，创建结果用户名快照 |
| created_at | DATETIME(6)，服务端时间，沿用课程时区与精度规则 |

唯一约束：uk_hospital_admin_operation_actor_key(actor_id, operation_key)、uk_hospital_admin_operation_admin(admin_id)。tenant_id 提供显式外键索引；actor_id/admin_id 的对应唯一索引满足外键索引要求。无级联删除、不保存密码/令牌/医疗正文、不提供修改或清理操作记录的接口。基础 ID 的 utf8mb4 列与原外键定义一致，索引字节预算需在迁移测试中验证教师 MySQL 5.6 兼容性，不以 MySQL 8 通过替代。

新增 005_hospital_onboarding.sql、对应保护性升级器和行为测试，更新新建 schema/JPA 注册。005 只在精确 004 基线上新增此表；已有账号、哈希、医院与临床数据原样保留，不填充历史操作表。

升级器必须检查目标名称、结构、约束、实例身份和实际成功的完整备份；不确定或部分 DDL 失败即停止，保留证据，不自动 DROP、覆盖恢复或放宽旧升级器。MySQL DDL 不承诺事务回滚。新版只读校验明确识别 005；旧 003/004 验证器拒绝新形状的行为继续保留。

新结构为 13 张应用数据库表；含幂等表的业务回滚比较应覆盖 12 张非 audit_event 表。已有冻结的 12 表验收助手与原始证据不改写、不在 005 上强行复用。当前临床/附件共享验收环境未结束前，不向它升级 005；新功能验收使用新、独立、受保护的环境。

## 6. 事务、锁序与停用即时生效

所有创建/启停操作由一个 EJB 数据库事务承载。原子开通同事务写 tenant、user_account、hospital_admin_operation 和一条成功审计；任一步失败全部业务写入回滚。失败审计仍由既有独立事务机制记录，不用补偿删除冒充原子性。

平台的医院/管理员写入统一顺序：已认证平台操作者 Account 排他锁并刷新 → 已有目标 Tenant 排他锁并刷新 → 目标医院管理员 Account（需要时排他锁并刷新）。一次操作只处理一家医院。既有医院冻结入口也采用此前置操作者锁，避免新旧入口锁序分叉。角色固定且平台账号 tenant_id 必须为空；锁后再次验证 ACTIVE/角色，不只相信 JWT 或首次读取。

新开通先锁平台操作者、查询其 operationKey；首次请求创建新医院，不锁其他医院。幂等重试依据原操作锁定其医院和管理员，然后比较输入与返回结果。增补/启停即使医院冻结也能取得医院排他锁，但不能使用会拒绝 DISABLED 的“医院业务可写”校验替代控制面校验。

同院新增/启停/冻结都在同一个 Tenant 排他锁内串行。最后管理员检查必须是锁后的当前读取，例如查找另一位启用管理员的带锁有限结果；不能使用事务早期的普通 COUNT 快照。两名平台操作者同时停用不同管理员时，后提交者必须看见前一位已停用，不能让两者都通过。

现有 HospitalDepartmentService、HospitalDoctorService、SlotAdminService 的每个写入口，在取得 Tenant 共享锁后，重新刷新并验证医院管理员账号、角色、所属医院和 ACTIVE；锁保持到事务结束，再执行原资源锁序及业务校验。新增停用操作先持有同院 Tenant 排他锁，因此：

- 医院写入先拿到共享锁：可以完成，停用等待其提交后生效。
- 停用先拿到排他锁：等待中的医院写入随后刷新身份并拒绝，不得用等待前已验证的账号继续写。

只读历史与冻结语义沿用现状。身份在每次请求重新检查，不承诺撤销已经开始并完成授权的纯读取；新停用账号后续读取和写入都被拒绝。医生创建的密码生成/交付、医生状态限制、患者/医生业务规则保持原样。

用户名跨创建入口竞争由既有全局唯一约束兜底。仅识别具体用户名唯一约束为 USERNAME_EXISTS；其他完整性错误不得误报为用户名冲突。操作唯一约束冲突也不能在已标记回滚的事务中继续读取并提交，需整笔失败后由客户端正常重试。

## 7. API、审计与错误

以下均在已有 /paas/api 前缀下，只允许已认证 PLATFORM_ADMIN；能够绑定的请求先验证身份角色再作业务校验。不可解析 JSON、未知字段等绑定错误与媒体类型错误由现有边界处理，不承诺尚未进入资源方法的失败具有已认证操作者。

| 方法与路径 | 请求或返回 |
| --- | --- |
| POST /platform/tenants | hospitalName、username、initialPassword、operationKey；安全创建结果 |
| GET /platform/tenants/{tenantId}/administrators | page 默认 1、size 默认 20/最多 100；管理员分页 |
| POST /platform/tenants/{tenantId}/administrators | username、initialPassword、operationKey；安全创建结果 |
| PUT /platform/tenants/{tenantId}/administrators/{adminId}/status | status、expectedStatus；安全管理员结果 |

现有医院列表/医院状态接口保留。新建编号用服务端 UUID；既有目标编号按原持久化 ID 处理，不要求把历史合法编号强制改成 UUID。ID 非空、不超过原 36 字符范围、无控制字符；URL 段正确编码，查询始终绑定参数。

管理员列表稳定按 username、id 排序，分页 offset 检查溢出；目标管理员仅投影 id、tenantId、username、status。列表业务查询不读取目标管理员 password_hash，不序列化任何哈希，不返回医生、患者、平台账号或临床数据；身份认证仍沿用现有机制。分页根对象包含 items、total、page、size、activeAdministratorCount，后者统计该院所有页面中的启用管理员，仅作页面提示，不代替状态变更时的锁后检查。目标账号与路径医院不匹配/角色不对返回通用 FORBIDDEN，不移动账号。

新请求拒绝未声明字段，尤其 role、tenantId、id、passwordHash。复用统一 ApiResponse/ApiError、服务端 requestId、JSON 大小边界及异常脱敏；成功与幂等成功均使用现有 HTTP 200 约定。

新增稳定业务码：HOSPITAL_ONBOARDING_INVALID（400）、USERNAME_EXISTS（409）、OPERATION_KEY_CONFLICT（409）、ADMIN_STATUS_CONFLICT（409）、LAST_ACTIVE_HOSPITAL_ADMIN（409）。已有 UNAUTHORIZED（401）、FORBIDDEN（403）、INTERNAL_ERROR（500）沿用。门户显示可操作中文提示，不返回原生异常、SQL、密码或请求对象。

审计事件：TENANT_OPEN→TENANT；HOSPITAL_ADMIN_CREATE/HOSPITAL_ADMIN_STATUS_CHANGE→新增 HOSPITAL_ADMIN_ACCOUNT。原子开通是一条 TENANT_OPEN，不再在同一请求额外创建 ADMIN_CREATE 成功事件；操作表关联首管理员。幂等与重复状态为 NO_CHANGE，首次成功为 SUCCESS。经核实的目标医院才附入成功审计；失败遵循原平台失败审计 tenant/object 为空的安全政策，不记录未验证目标。审计过滤器、路由映射、查询枚举、门户事件标签及测试同时更新。

## 8. 门户体验与秘密边界

平台页增加“开通医院”入口；每家医院提供“管理员”分页链接。独立管理员页显示医院名称/编号/冻结提示、账号列表、增补入口和启停表单。最后一位启用管理员的停用按钮可给出只读原因，但服务端检查是最终依据。

开通表单包含医院名称、用户名、初始密码与确认密码；增补表单不再要求医院名称。两者包含独立 operationKey 和现有 CSRF token。状态表单带 expectedStatus。无 JavaScript 仍可完成全流程，使用键盘可达的原生控件、明确 label、错误区域、焦点提示；所有动态文本和属性经过现有 HTML 转义。

失败保留非密码输入及 key；成功页只显示编号、名称、用户名和后续进入管理员列表的链接，明确密码由操作者保管、页面不提供找回。已有医生一次性密码展示页面完全不改。

敏感表单/结果设置 no-store；密码输入 autocomplete=new-password。服务器不把初始密码或确认值放进 URL、HTML value、会话/flash、幂等表、审计、错误消息、日志或测试公开输出；仅本次请求和 BCrypt 校验期间存在于内存。Portal/PaaS 日志脱敏及验收扫描必须覆盖新增 JSON/form 字段名，不能只检查既有 password 字段。浏览器密码管理器的用户自主保存不等于服务器持久化。

## 9. 测试与交付验收

测试先行，按契约、数据库业务/API、门户、保护升级及真实环境分层；源码或替身通过不替代实机观察。至少覆盖：

1. 原子成功恰好一院一管理员一操作记录一成功事件；在账号、操作记录或审计写失败时无新医院/账号/操作残留，独立失败审计符合原机制。
