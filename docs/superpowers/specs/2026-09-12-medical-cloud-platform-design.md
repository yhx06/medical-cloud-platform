# 多租户医疗云平台基础框架设计

## 1. 目标

本阶段建立一个能够启动、登录和验证租户隔离的课程项目基础框架，为后续预约、接诊、电子病历、模拟缴费、对象存储和统计功能提供稳定边界。基础框架必须可以由新组员在本地复现，并能通过自动化测试证明角色权限与租户隔离有效。

## 2. 范围

本阶段实现以下能力：

- Spring Boot 后端和 Vue 3 前端可独立启动。
- MySQL 与 MinIO 可通过 Docker Compose 启动。
- 系统预置两个虚拟医疗机构及患者、医生、医院管理员、平台运营管理员四类角色。
- 用户可以登录、刷新登录状态并查询当前用户信息。
- 后端从认证信息中解析租户上下文，不接受客户端直接指定可信租户。
- 页面根据用户角色展示工作台和功能入口，未登录用户不能访问受保护页面。
- 统一成功响应、错误响应、参数校验、异常处理和请求日志规范。
- 为预约、诊疗、病历、订单、文件和统计建立模块边界、核心状态与导航入口。
- 提供健康检查、数据库迁移、开发配置、测试配置和启动说明。

本阶段不实现完整业务 CRUD、真实支付、真实患者数据、AI 自动诊断、DICOM 处理、微服务治理或生产级高可用。

## 3. 方案选择

采用前后端分离的模块化单体。它保留清晰的业务模块与接口，同时只需维护一个后端应用、一个前端应用和一套数据源，适合课程周期与多人协作。微服务会引入网关、注册发现和分布式一致性成本；普通分层单体则容易把不同业务的控制器、服务与数据访问代码混在一起。

## 4. 技术栈

- 后端：Java 21、Spring Boot 3、Spring Security、JWT、Spring Data JPA、Flyway、Bean Validation、Maven。
- 前端：Vue 3、TypeScript、Vite、Pinia、Vue Router、Axios、Element Plus、Vitest。
- 数据与运行：MySQL 8、MinIO、Docker Compose。
- 测试：JUnit 5、Spring Boot Test、Spring Security Test、H2 MySQL 兼容模式、Vitest。

## 6. 身份、角色与租户模型

`UserAccount` 是平台级账号，包含账号名、密码哈希、状态和角色。医生与医院管理员必须绑定一个租户；患者属于平台级账号，可以选择不同机构预约，但每条预约及其后续数据只属于一个租户；平台运营管理员不绑定具体租户，只能管理租户基础信息和读取脱敏汇总。

角色固定为：

- `PATIENT`：查询机构与号源，管理本人预约和记录。
- `DOCTOR`：处理本租户且分配给本人的预约与病历。
- `HOSPITAL_ADMIN`：维护本租户科室、医生、号源并查看本机构统计。
- `PLATFORM_ADMIN`：维护租户状态并查看跨租户脱敏指标。

JWT 中记录账号标识、角色和可选租户标识。后端认证过滤器创建不可变的 `CurrentUser`；业务服务从 `CurrentUser` 获取租户上下文。患者跨机构操作时，目标租户必须由所访问的业务对象或受控查询结果确定，不得信任请求头或请求体中任意提交的 `tenantId`。

## 7. 登录与页面数据流

1. 用户向 `POST /api/auth/login` 提交账号和密码。
2. 后端验证账号状态与密码哈希，返回短期访问令牌和用户摘要。
3. 前端认证 Store 保存会话，Axios 请求拦截器携带令牌。
4. 页面刷新时，前端调用 `GET /api/me` 恢复用户、角色和租户信息。
5. Vue Router 根据 `route.meta.roles` 判断页面访问权限；后端仍以 Spring Security 方法或路由规则进行最终授权。
6. 注销时前端清除令牌和用户状态并返回登录页。

基础框架提供以下可用接口：

- `POST /api/auth/login`
- `GET /api/me`
- `GET /api/platform/tenants`，仅平台运营管理员可用
- `GET /api/hospital/profile`，仅医生和医院管理员可读取本租户信息
- `GET /api/patient/profile`，仅患者可读取本人信息
- `GET /actuator/health`

## 8. 业务模块边界

预约模块定义 `BOOKED`、`IN_PROGRESS`、`COMPLETED`、`CANCELLED` 状态；订单模块定义 `PENDING`、`PAID`、`CANCELLED` 状态。本阶段只建立枚举、包结构、前端入口和必要的公开接口类型，不创建没有行为的数据库表或空 Repository。

后续核心数据链为：预约确定租户和医生，接诊引用预约，病历由接诊生成，订单由完成接诊触发，文件元数据关联患者、预约和租户。任何跨实体查询都必须同时校验主体权限和 `tenant_id`。

## 9. 数据库与初始化

Flyway 首个迁移建立 `tenant`、`user_account` 和必要关联表，并创建索引与唯一约束。开发数据迁移预置租户 A、租户 B 及可公开演示的虚构账号。密码只保存 BCrypt 哈希。

运行环境使用 MySQL 8。自动化测试使用 H2 的 MySQL 兼容模式执行同类约束和安全测试，使测试不依赖 Docker 守护进程。涉及 MySQL 专有语法的迁移必须在 Docker Compose 环境中另行执行一次迁移验证。

## 10. 前端设计

登录成功后进入统一主布局，左侧菜单由角色生成：

- 患者：工作台、预约挂号、我的预约、病历与订单。
- 医生：工作台、待接诊、接诊记录。
- 医院管理员：工作台、科室医生、排班号源、机构统计。
- 平台运营管理员：工作台、租户管理、平台统计。

本阶段除登录、工作台和身份摘要外，其余入口使用明确的“模块尚未实现”页面，并展示对应后端模块边界，避免制造已经完成业务功能的假象。

## 11. 错误处理与日志

API 错误统一返回 `code`、`message`、`requestId` 和可选 `fieldErrors`。基础错误码包括 `AUTH_INVALID_CREDENTIALS`、`AUTH_FORBIDDEN`、`VALIDATION_ERROR`、`TENANT_ACCESS_DENIED`、`RESOURCE_NOT_FOUND` 和 `INTERNAL_ERROR`。

请求日志记录请求标识、账号标识、租户标识、方法、路径、状态码和耗时，不记录密码、令牌、病情正文或其他敏感字段。未处理异常向客户端返回通用信息，详细堆栈只写入服务端日志。

## 12. 安全约束

- 除登录和健康检查外，API 默认要求认证。
- 密码使用 BCrypt，JWT 密钥由环境变量提供，示例配置不得包含生产密钥。
- 前端路由守卫只改善交互，不能替代后端授权。
- 数据查询必须按当前租户收敛；平台运营管理员读取跨租户数据时只能调用专门的脱敏汇总接口。
- 演示数据全部虚构，不使用真实身份证、病历或医学影像。
- MinIO Bucket 默认为私有，后续文件访问必须由后端授权并生成短期签名地址。

## 13. 测试策略

后端测试至少覆盖：有效登录、错误密码、禁用账号、未认证访问、四角色授权矩阵、医生与医院管理员仅访问本租户、租户 A 不能读取租户 B、平台运营管理员不能读取病历正文、Flyway 在测试数据库成功迁移。

前端测试至少覆盖：登录成功跳转、登录失败提示、刷新恢复会话、未登录路由拦截、角色菜单差异和无权页面跳转。端到端人工验收使用两个租户的演示账号验证界面与接口行为一致。

## 14. 验收标准

- `mvn test` 与 `npm test` 全部通过。
- `mvn spring-boot:run` 能启动后端，`npm run dev` 能启动前端。
- Docker Compose 能启动 MySQL 与 MinIO，后端完成数据库迁移并通过健康检查。
- 四类演示账号均能登录并看到对应菜单。
- 越权接口返回 403，未认证接口返回 401，租户越权测试能够稳定复现并通过。
- README 或开发文档包含环境要求、启动顺序、演示账号和测试命令。

## 15. 后续扩展顺序

基础框架验收后，按“号源与预约 → 接诊与病历 → 订单与模拟支付 → 文件服务 → 统计与审计”的顺序扩展。AI 辅助保持为 P2，只有核心闭环和租户隔离测试通过后才进入开发。
